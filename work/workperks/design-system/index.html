WorkPerks design system

The foundations, components and rules for building the WorkPerks employee app and HR portal. Every value here starts from the WorkPerks website, then is tightened for product use: a 4px grid, contrast that passes, a real error colour, and states the marketing site never needed.

Start with foundationsStart with foundations Get the tokens
Employee app

Mobile first, 360–430px. Allowance, benefits, claims and rewards. Shows only what applies to the person, and says why when something is blocked.

HR portal

Desktop first, 1280px and up. Eligibility, bands, caps, approvals and reporting across every entity from one console. Counts, never individuals.

One system underneath

Both surfaces read the same semantic tokens and components, so what HR configures and what employees see always look like the same product.

Principles

Six rules taken straight from what the product promises on the website. When a design decision is unclear, one of these usually settles it.

01

Absent, not greyed out

If a module is off for someone, it is not on their screen. No disabled tiles, no dead ends, no support ticket asking why.

02

Say the reason

When something is blocked because a cap is reached or a window has shut, say so where the person is looking, with what they can do next.

03

Counts, never individuals

HR sees eligibility and totals. What one person booked stays with them, and the interface tells them so in plain words.

04

Money is exact

Amounts are tabular, rupee-formatted and never rounded silently. Cover is applied before a price is shown, not after.

05

Set once, change anytime

Configuration is a setting, not a project. HR screens make the current rule visible and the change reversible.

06

Bold in one place

Anton, colour blocks and the highlight marker are loud. Each screen gets one loud moment; everything around it stays calm and white.

Forms and validation

One column on phones. Labels above fields. Validate a field when someone leaves it, and the whole form when they submit. A claim can't be sent without what it needs, so it never comes back a week later.

Error messages

Say what's wrong and how to fix it, in one sentence: "Enter an amount up to ₹1,500." Not "Invalid input". Not "Oops".

Order of errors

On submit, move focus to the first field with an error and announce the count: "2 things to fix before sending."

Required vs optional

Most fields are required, so mark the optional ones with "Optional" in the label. Never use an asterisk alone.

Inputs that help

Use inputmode="decimal" for money, numeric for codes, email for work email. Format rupees as the person types.

Guidance

Accessibility

WCAG 2.2 AA is the floor. The components on this page already meet it; these are the things that break when they're combined carelessly.

  • Contrast4.5:1 for text, 3:1 for icons and large text. White text never on orange, amber or brand green-600.
  • Focus is always visible3px blue outline, 3px offset. Never remove it; restyle it if you must.
  • Touch targets 44pxSmall icon buttons (32px) get extra hit area with padding or spacing.
  • Colour is never the only signalStatus pills have text. Charts have legends. Errors have an icon and words.
  • Reduced motionAll transitions drop to near-zero, marquees stop, progress bars appear filled.
  • Text scales to 200%Use tokens, not fixed heights on text containers. Rows grow; they don't clip.
  • Semantics firstReal buttons, labels tied to inputs, aria-expanded on accordions, role="tab" on segments.
  • DialogsTrap focus, close on Escape, return focus to the trigger, label with the title.

Tokens and code

One source, four files. The two CSS files are exactly what this page runs on. The JSON follows the W3C design tokens format for Figma Tokens Studio or Style Dictionary. The Tailwind config maps every token onto utilities for the React builds. Download each file from the bar below.


  

  
Naming
Primitives describe the value. Semantic tokens describe the job.

  

    
--wp-blue-600
Primitive. family-step. Only used inside semantic tokens and illustrations.

    
--wp-action-brand
Semantic. role-variant. What components read. Changes value in dark mode.

    
.wp-btn--brand
Component. block--modifier, block__element. Every class is prefixed wp- so it never collides with app code.

  

  
Using a component in React

  
// Button.tsx — thin wrapper over the CSS contract
type Variant = 'primary' | 'brand' | 'accent' | 'secondary' | 'outline' | 'ghost' | 'danger';
type Props = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: Variant; size?: 'sm' | 'md' | 'lg'; disc?: boolean; block?: boolean; loading?: boolean;
};

export function Button({ variant = 'primary', size = 'md', disc, block, loading, children, className = '', ...rest }: Props) {
  const cls = ['wp-btn', `wp-btn--${variant}`, size !== 'md' && `wp-btn--${size}`,
    disc && 'wp-btn--disc', block && 'wp-btn--block', className].filter(Boolean).join(' ');
  return (
    <button className={cls} aria-busy={loading || undefined} {...rest}>
      {disc && <span className="wp-btn__disc"><Icon name="arrow" /></span>}
      <span className="wp-btn__label">{children}</span>
    </button>
  );
}
