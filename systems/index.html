Chapter 01 — What it is

A system is only infrastructure once other people can build on it without asking you first.

Capsule is the organisation’s first design system: five written principles, six foundation areas, a token layer, twenty-five specified components and four platforms. It is documented twice over — as a Figma file engineers read, and as a written construction blueprint that states every value as a number.

Chapter 02 — The challenge

One product ecosystem. No shared language.

Three products, built by different teams at different times, each with its own idea of what a button was.

  • 01

    Every screen re-decided the basics

    Colour, spacing and type were settled per screen rather than once, so the same control looked different in two places.

  • 02

    Design and engineering guessed at each other

    Without named values, a handoff was a screenshot and a conversation. The same component got rebuilt per platform.

  • 03

    Four platforms, four answers

    App, MWeb, DWeb and PWA each needed their own sizing — but nothing recorded what was deliberately different and what had simply drifted.

  • 04

Chapter 03 — The decision

Not another UI kit. A foundation for how we build.

A kit is a folder of components someone has to remember to open. A system is a chain of decisions where each layer only depends on the one above it — so a change enters once and arrives everywhere.

Five principles, written down

These settle arguments. They are quotable by someone who is not me, which is the only test that matters.

  • Trust & clarity

    Blue-dominant palette conveys reliability. Clean layouts with ample whitespace.

  • Hierarchy

    Orange and yellowish-orange accents draw attention to key actions and alerts.

  • Consistency

    Every component shares the same radius scale, spacing grid and colour tokens.

  • Accessibility

    Primary blue on white exceeds WCAG AA (4.65:1). Interactive targets are minimum 44px.

  • Light-first

    Design primarily for light mode — white surfaces, subtle grey borders, minimal shadows.

The chain

  1. 1 Principles Five written rules that decide arguments before they start. 5 principles
  2. 2 Foundations Colour, type, space, elevation, radius, icons. 6 areas
  3. 3 Tokens The named values the foundations resolve to. primitive + semantic
  4. 4 Atoms The pieces that cannot be broken down further. 5
  5. 5 Components The library, with states and behaviour specified. 25
  6. 6 Patterns The recurring compositions above component level. 4
  7. 7 Products App, MWeb, DWeb, PWA. 4 platforms

Each layer only depends on the one above it. That is the whole reason a brand decision can be made once: it enters at the token layer and arrives everywhere below.

Radius

Radius scale

  • radius-xs 4px Tags, chips, small buttons, badges
  • radius-sm 8px Medium and large buttons, inputs, dropdowns, search

What the measurement found

The blueprint states that primary blue on white is 4.65:1. Measured, it is 6.64:1 — the system is more accessible than its own documentation claims.

But 4 of the 14 pairs fall below 4.5:1 — muted text, warning text, the disabled button label and the caution tag. Placeholder and disabled text are partly exempt under WCAG; warning copy and the caution tag are not. This is worth a look before the next version of the system.

Chapter 05 — Architecture

From individual values to a system of decisions.

The difference between a palette and a token layer is one word: job. A primitive says what a colour is. A semantic says what it is for.

Primitive

A value with a name. Blue-400 is #005DAC and means nothing else.

Semantic

A value with a job. border-input-focus happens to be Blue-400 today; the component never needs to know that.

Component

Consumes semantics only. Re-point one semantic token and every component using it moves together.

The semantic map, as documented

  • bg-page → White #FFFFFF
  • bg-surface → BlushGray-100 #EFF2F4
  • bg-extralight-primary → Blue-100 #F0F9FF
  • bg-extralight-success → Green-100 #E8FCCF
  • bg-extralight-error → Red-100 #FCEDEE
  • bg-extralight-tertiary → YellowOrange-100 #FFF3E0
  • bg-overlay → Black @ 40% rgba(0,0,0,0.4)
  • border-card → BlushGray-100 #EFF2F4
  • border-divider → Gray-100 #F2F2F2
  • border-input → BlushGray-200 #D2DAE0
  • border-input-focus → Blue-400 #005DAC
  • border-input-error → Red-400 #DA1E28

Twelve semantic tokens from the blueprint, each resolved to the primitive behind it. This is the layer that makes a brand change a one-line edit.

The cheat sheet, verbatim

Do

  • Use Rubik for every piece of text.
  • Use the documented radius scale — 4px for small controls, 8px for medium and large.
  • Keep interactive targets at 44px minimum.
  • Use semantic tokens rather than raw hex values.
  • Keep shadows subtle and uncoloured.

Don’t

  • Never substitute the typeface.
  • Never make buttons pill-shaped.
  • Never use coloured or hard drop shadows.
  • Never invent a colour outside the documented scales.
  • Never go below the 44px touch target.

The blueprint closes with these. A rule a designer can quote is worth more than a review meeting that reaches the same conclusion privately.

Chapter 11 — What I learned

The system is the product behind the products.

  1. 01

    Designing for scale

    A system is a product whose users are designers and engineers. The moment I started treating the blueprint as a spec with versions rather than a document, arguments got shorter.

  2. 02

    Design and engineering

    Named values are the whole trick. A hex code in a comp is a suggestion; `border-input-focus` is a contract.

  3. 03

    Rules beat taste at scale

    Five written principles settle more disagreements than any amount of review, because they are quotable by someone who is not me.

  4. 04

    Governance is the hard half

    Launching a library is a project. Keeping one true is an operating commitment, and it is the part I would resource differently next time.

  5. 05

    Consistency against product need

    Four platforms needed four button heights. The system's job was to record which differences were deliberate — not to pretend there were none.

A design system is the product behind the products. When it works, nobody mentions it — they just ship faster and argue less, and the things they ship look like they came from the same company.
